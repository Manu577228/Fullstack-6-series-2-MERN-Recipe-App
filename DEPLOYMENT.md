# Recipe App: complete deployment (React + Express + MongoDB + Redis)

The Render Blueprint provisions three services: a static React site, an Express
API, and a **Redis-compatible** managed Key Value cache. MongoDB Atlas is a separate
managed database. Redis is connected to the API through a Render-provided internal URL.

> Render Key Value currently runs Valkey (Redis-protocol compatible) for newly
> provisioned services, not the Redis server implementation. The app uses the
> node-redis client, Redis commands, TTLs and Redis-style caching. If your resume
> specifically requires the Redis server, use a managed Redis service such as
> Redis Cloud, and provide its `REDIS_URL` manually rather than provisioning
> Render Key Value.

## Security
Both backend and frontend `.env` files were tracked in older commits. The
deployment change removes them from the current branch, but Git history
retains their contents. Rotate any real MongoDB credentials, Redis passwords,
JWT secrets and other exposed secrets. Never commit your replacement secrets.

## Deploy
1. Create a MongoDB Atlas cluster, DB user and connection string. Configure
   its network access to permit your Render API connections (restrict where
   possible).
2. In https://dashboard.render.com/blueprints, connect this GitHub repository
   and select the branch containing `render.yaml` (usually `master` after
   merging the deployment PR).
3. Set the `MONGO_URI` secret for the API. `JWT_SECRET` is generated by Render.
4. Set `CLIENT_ORIGIN` on the API to the exact HTTPS origin of your static site,
   e.g. `https://manu-recipe-app.onrender.com`.
5. Set `REACT_APP_API_URL` on the frontend to the actual HTTPS API origin,
   e.g. `https://manu-recipe-api.onrender.com`. It is compiled in at build time.
6. Verify the Blueprint creates the managed cache and automatically injects
   `REDIS_URL` into the API using `fromService`.
7. Deploy/redeploy both services if hostname values were changed.

## Test the complete architecture
- Visit `https://<API-HOST>/health` and expect `{"ok":true}`.
- Open the static site, register, log in and create a recipe.
- Visit the authenticated `GET /recipes` endpoint twice with the same token:
  the first response should have `X-Cache: MISS` and the next one
  `X-Cache: HIT`, while the cache is connected.
- Create or edit a recipe and fetch the list again: expect a cache miss
  because the API invalidates its user-list cache.
- Test update, save, unsave and delete, and refresh a frontend deep link.
- Check backend logs for `Redis connected`. If Redis cannot connect, the API
  falls back to MongoDB; it does not claim a hit. For a resume demo, verify a
  real HIT before calling it a deployed cache.

## Local
- Backend: `cd recipe-app-backend && cp .env.example .env && npm ci && npm run dev`
- Frontend: `cd recipe-app-frontend && cp .env.example .env && npm ci && npm start`
- Optional local Redis: `docker run -d --name recipe-redis -p 6379:6379 redis:7-alpine`
  then set `REDIS_URL=redis://localhost:6379` in the backend's local `.env`.

## Cost notes
Render service and Key Value plans can incur charges; review the checkout
screen before creating resources. The managed cache is in-memory, while Atlas
is the persistent source of truth.
